# Steno 1.1 Release Checklist

This checklist records what must be true before Steno 1.1 is tagged and published, and the receipts that prove it. The release itself follows the [1.0.1 release procedure](1.0.1-checklist.md) with `1.1.0` in place of `1.0.1`. This page adds the checks that are specific to 1.1 and collects their results in one place.

## Current stage

1.1 is not yet published. The latest published release is 1.0.1. `project.yml` declares `1.1.0`, build `5`, and the 1.1 changes are listed under `## [1.1.0]` in the [changelog](../../CHANGELOG.md), with a date that is updated to the actual release date if it changes. The README and the source setup guide describe 1.1.

1.1 is a redesign of every window, panel and overlay, together with new recording, History and insertion features. The [1.1 design record](../design/1.1-design-record.md) explains the design decisions.

A passing result applies to the source and build it ran against. A new code change needs proportionate revalidation. Do not carry a result forward without checking what changed since it was recorded.

## Known limits carried to 1.2

These are accepted for 1.1 and recorded here so they are not mistaken for regressions.

- **Quitting during an unanswered media pause.** If Steno quits while a pause it sent for an Option dictation is still unconfirmed, the paused app is not resumed. The media rules send Play only to an app Steno observed stopping, and an unconfirmed pause is never treated as Steno's, so this follows the rule. For a hands-free dictation, quitting already waits for the pause to be answered and resumes the app if Steno saw it stop. Resolving the confirming-Option case needs a teardown wait in the media service and is planned for 1.2.

What differed from the procedure:

- Step 4 rested on the maintainer's everyday use of Developer ID signed local builds of the 1.1 branch from October 2 to October 13 and on the live acceptance ledger above, not on the CI preview artifact.
- Step 8: the hosted tests on macOS 26 failed twice in the Release run on one test, "Discard on the island throws a long recording away, and Undo on it inserts it once". The island stayed on listening, so the discard was never held for Undo. The same test passed in 35 ms on both pull request runs and on main's run. Only the failed jobs were re-run, and the third attempt passed. The test discards before the recording's start has finished, and the previous test's session closes without being awaited; the test fix follows the release.
- Step 11: the DMG was checked against `SHA256SUMS`, its attestation verified against `release.yml` at `4ae0c5a`, its stapled ticket validated and Gatekeeper accepted it as Notarized Developer ID. The app inside passed a strict deep `codesign` check and Gatekeeper, and its Info.plist reads 1.1.0, build 5. The app was not launched, because a 1.1 test build with the same bundle identifier was running against the maintainer's data. The notes were set through the API with `tag_name` and `target_commitish`, and the draft stayed attached to `v1.1.0`.
- GitHub's own CodeQL check on pull request 35 reported the three reviewed runtime-helper findings as new in changed code, because the window recovery moved them. They remain open on main as before, and Security Gate, which checks them against the reviewed record, passed.
