# Steno 1.0.1 Release Procedure

This is the order of operations for releasing 1.0.1 through the standard [Release workflow](../ci-cd.md#release-operation). It records the steps that no workflow enforces. Each step lists the action, how to confirm it worked, and what to do if it did not.

Two facts shape the whole procedure:

- **A version tag is permanent.** A repository rule prevents moving or deleting `v1.0.1`. Every check that can run before the tag exists runs before it.
- **Parts of the release path have never completed in their standard form.** Draft lookup, attestation verification against `release.yml`, and publication first run for real during this release. The rehearsal exercises everything up to signing and notarization; it cannot exercise those later steps.

Throughout, `<sha>` is the full 40-character release commit on main.

## 1. Prepare the release pull request

**Action.** In the pull request that finishes 1.0.1:

- Set `MARKETING_VERSION` to `1.0.1` and raise `CURRENT_PROJECT_VERSION` above 1.0.0's build `3` in `project.yml`.
- Move the changelog entries from `[Unreleased]` into `## [1.0.1] - YYYY-MM-DD`, using the intended release date, and leave `[Unreleased]` without entries.
- Update version wording in `QUICKSTART.md` and the README.
- `project.yml` is bound by the [reviewed CodeQL findings](../maintainers/reviewed-codeql-findings.md), so C/C++ analysis fails until that record is reviewed again for the changed files. Complete that review in this pull request.

**Confirm.** `CI Gate` and `Security Gate` pass on the pull request, and on the pull request branch:

```bash
python3 scripts/ci/release-guard.py plan 1.0.1
```

reports no failures. Fetch tags first if it cannot find `v1.0.0`.

**If not.** Fix the pull request. Nothing permanent has happened yet.

## 2. Close the release window to other changes

**Action.** Before merging, merge or close any open dependency-update pull requests so none lands during the release. After merging the release pull request, merge nothing else to main until the release is published.

**Confirm.** Main's head is the release pull request's merge commit, `<sha>`:

```bash
git fetch origin main
git rev-parse origin/main
```

**If not.** Another change reached main. Treat the new head as the release candidate and repeat steps 3 to 5 for it. Do not tag an older commit: the Release workflow requires the tagged commit to be main's head when it is dispatched.

## 3. Wait for main's own runs to finish

**Action.** Wait for the CI and Security runs triggered by the merge to finish. Do not dispatch anything while they are running: the release needs the same macOS runners, and at most five macOS jobs run at once.

**Confirm.** Both runs for `<sha>` show success in the Actions tab. Every main run uses full validation, so a documentation-only release commit still has complete tests and a preview.

**If not.** Diagnose the failing job before re-running anything. A real defect is fixed in a new pull request, which produces a new candidate; return to step 1. No tag exists yet.

## 4. Accept the preview build

**Action.** Install `unsigned-preview-arm64-<sha>` from the main CI run and complete the native-app acceptance from the [1.0 checklist](1.0-checklist.md#native-app-acceptance): microphone capture, insertion, permissions, supported media applications and the interface. The artifact is kept for seven days. It is ad-hoc signed and is not the shipped configuration.

**Confirm.** Each acceptance item is recorded as passed, or any gap is explicitly accepted.

**If not.** Fix it in a new pull request and return to step 1.

## 5. Check the release facts at the exact commit

**Action.** On a clean checkout of main at `<sha>`:

```bash
git fetch origin main --tags
git switch --detach origin/main
python3 scripts/ci/release-guard.py plan 1.0.1
```

**Confirm.** Every line is `ok:` and the command ends with `Release plan for 1.0.1 passed`. A `note:` that the changelog date is not today is acceptable only if that date is the intended release date.

**If not.** Each `FAIL:` names the fact to correct. Correct it in a pull request and return to step 2. If the distribution entitlements changed on purpose, review that change before acknowledging it with `--accept-entitlements-change`.

## 6. Rehearse signing and notarization

**Action.** Run **Actions → Release rehearsal → Run workflow** on main with version `1.0.1` and mode `full`, then approve the **release** environment when asked. The rehearsal runs the `plan` check again, builds the app, signs it and its bundled runtime, notarizes once, staples and verifies Gatekeeper. It cannot tag, draft, publish or attest, and uploads only a notary receipt and a hash summary.

**Confirm.** The run succeeds, its notary receipt reports `Accepted`, and main's head is still `<sha>`.

**If not.** Nothing permanent has happened. For a credential, keychain or certificate failure, correct the release environment's secrets and run the rehearsal again; mode `signing` checks credentials in about a minute. For a notarization rejection or a build failure caused by the code, fix it in a pull request and return to step 1.

## 7. Create the tag by hand

**Action.** Only after steps 3, 5 and 6 are green for the same `<sha>`:

```bash
git fetch origin main
test "$(git rev-parse origin/main)" = <sha>
git tag v1.0.1 <sha>
git push origin v1.0.1
```

**Confirm.** `git ls-remote origin refs/tags/v1.0.1` prints `<sha>`.

**If not.** If the push was refused, check whether the tag already exists and where it points. A tag pushed at the wrong commit cannot be moved; 1.0.1 is then spent and the release continues as 1.0.2 from step 1.

## 8. Dispatch the release with publication enabled

**Action.** From **Actions → Release → Run workflow** on main, enter version `1.0.1`, source SHA `<sha>`, confirm manual acceptance, and set `publish_release` to true. Publishing in the same run means the separate **Publish release** workflow, which has never run, is not needed.

**Confirm.** The preflight job passes, then the validation and security jobs pass, which takes about an hour.

**If not.** A flaky job may be re-run with **Re-run failed jobs** after the cause is understood; this re-runs the same code at the tag. A failure caused by the code at the tag means 1.0.1 is spent: the tag stays, and the fix ships as 1.0.2.

## 9. Approve signing

**Action.** Approve the **release** environment.

**Confirm.** The signing job succeeds and its notary receipt artifact reports `Accepted`.

**If not.** If the failure happened before notarization, such as a transient network or service error, re-run the failed job. If the notarization outcome is unclear, inspect `notary-recovery-<run-id>-<attempt>` and query that submission before any new upload, as described under [failure recovery](../ci-cd.md#failure-recovery). A failure caused by the code at the tag means 1.0.1 is spent and the fix ships as 1.0.2.

## 10. Approve the draft

**Action.** Approve the **release-draft** environment.

**Confirm.** The draft job succeeds and a draft release `v1.0.1` holds `Steno-1.0.1.dmg`, `SHA256SUMS` and `release-manifest.json`.

**If not.** If the job fails after the draft was created, for example while looking the draft up, **do not re-run it**; a second run refuses the existing draft. Find the draft by its numeric ID from the authenticated release list:

```bash
gh api --paginate repos/Ankit-Cherian/steno/releases \
  --jq '.[] | select(.tag_name == "v1.0.1") | {id, draft, assets: [.assets[].name]}'
```

Then publish that exact ID, either with the **Publish release** workflow (main must still be at `<sha>`, and it re-runs validation) or by a deliberate maintainer publication by ID, recording why.

## 11. Accept the signed download and write the notes

**Action.** Download the draft's DMG, check it against `SHA256SUMS`, and verify its provenance:

```bash
gh attestation verify Steno-1.0.1.dmg --repo Ankit-Cherian/steno \
  --signer-workflow Ankit-Cherian/steno/.github/workflows/release.yml
```

Install and open it; this is the only test of the actual signed bytes. Then replace the draft's placeholder notes with the approved 1.0.1 notes, in the browser. If the notes are set through the API instead, send `tag_name` and `target_commitish` together with `body`: an update that carries only `body` detaches the draft from its tag, and the publish job then rejects it. Nothing checks the notes themselves.

**Confirm.** The checksum and attestation match, the installed app reports version 1.0.1, and the draft shows the final notes.

**If not.** Leave the draft unpublished. A defect in the signed build means 1.0.1 is spent, and the fix ships as 1.0.2.

## 12. Approve publication

**Action.** Approve the **release-publish** environment.

**Confirm.** The publish job succeeds, `v1.0.1` is the latest release, and the [latest download link](https://github.com/Ankit-Cherian/steno/releases/latest) resolves to it.

**If not.** If the job fails after its publication request, **do not re-run it**; the release may already be public. Read the release by its ID and check `/releases/latest` before doing anything else.

## 13. Close the release

**Action.** Record the run, tag, release ID and installer SHA-256 in the release record. Update any separately maintained website version text. Main can accept changes again.

**Confirm.** The download link, version text and release record agree on 1.0.1.

## Record of the 1.0.1 release

Published October 2, 2026 at 20:05 UTC. Release [v1.0.1](https://github.com/Ankit-Cherian/steno/releases/tag/v1.0.1), ID 402117854, tag `v1.0.1` at `184d261c8bea5213b5fcc58c7492568fc91a3f5b`, produced by Release run [37050792045](https://github.com/Ankit-Cherian/steno/actions/runs/37050792045). `Steno-1.0.1.dmg` is 458,654,507 bytes with SHA-256 `6a7d1c0fab24e02c095f0f8f9155483708e9214c4ee5b2fa821c530e85512729`; its notarization submission was accepted. The rehearsal (run 37049303743) had been accepted earlier the same day.

What differed from the procedure above:

- Step 4 rested on the maintainer's tests of Developer ID signed local builds of the same app code rather than on the CI preview artifact. Media pausing in Podcasts, Music and a Chrome video, dictation from Steno's own window, and permissions were checked; Spotify, longer pause intervals, microphone disconnection, a fresh user account and macOS 13 to 15 were not, and those gaps were accepted.
- Step 10: the first draft job was cancelled at its 10-minute limit while downloading the signed artifact, before any draft existed. Only the failed jobs were re-run; signing and notarization were not repeated. The time limits were raised afterwards.
- Step 11: the draft's notes were set through the API with only `body`, which detached the draft from its tag. It was reattached to `v1.0.1` with the same target commit before publication, and the publish job re-verified the tag, target and asset digests.
